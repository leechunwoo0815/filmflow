## 未闭合的那一条（就是它让这次运行没打 PASS）

```text
✗ AssertionError: 交付失败：None None
  位置：scripts/e2e_fr40_keyboard.py:641
```

根因**不是产品**：`GET /jobs/{id}` 返回的是 `table_dict(Job)` 的**列名**
（`error_code` / `error_msg` / `result_json`，见 `server/app/models.py:287`），
而断言读的是驼峰 `errorCode` / `errorMsg` 与 `result` → 全部取到 None，
于是把一个 `status=succeeded` 的作业读成了"失败且没有原因"。
同一条陷阱本批已经踩过一次（`payload` vs `payload_json`），属于"读接口返回形状靠猜"的代价。

修法（三行，见交接文档 §6）：键名改成列名，并在断言里把整段 body 的头 200 字符打出来，
这样下次再撞至少能看到真实字段。

## attempt 14（2026-11-07 晨）：断言修好后，交付真的失败了——attempt 13 的「交付成功」是误读

键名修成列名 + body 头部 200 字进断言之后，第一次复跑就给出了**真实错误**：

```text
✓ 1–42（同 attempt 13，另有第 43 步）
✓ 43. A05 自动携带确认：policy=inherit author=local note=对比后选定 · H_现成版式
     （键盘签 7 + 自动 1 = 8 道门全覆盖）——2026-11-07 审计的两条 A05 断言在活 Run 上通过
✗ AssertionError: 交付失败：E_DELIVERY_FAILED E_DELIVERY_QC: ['captions']
  ｜body 头部：{'id': 158, 'kind': 'delivery', 'status': 'failed', 'payload_json':
  {'projectId': 228, 'runId': 336, 'profile': 'final'}, ...}
```

两个结论：

1. **attempt 13 的「Run 与交付本身都成功了」是错的。** `assert status == "succeeded"` 挂掉时
   渲染的正是读错的驼峰键（`None None`）——当时 `status` 就是 `failed`，错误原因被键名 bug
   一起吞掉了。上一版报告把断言语义读反了（把"断言失败"当成了"断言里拿不到原因"）。
   交接文档 §5 的前提「产品没问题，是测试自己在猜形状」同样要更正：**形状是猜了，但产品侧交付也真挂了。**
2. **根因是 3s 压缩与字幕 QC 的数学冲突，不是 QC 太严。** 292 字旁白 ÷ 3 秒 ≈ 97 字/秒，
   `delivery.MAX_CAPTION_CPS = 9` 必挂；自然时长 39.5s ≈ 7.4 字/秒在判据内。
   压缩是为省渲染时间加的，副作用是把交付判据变成必挂——又被不透明的断言藏了两天。

修法（已进脚本，attempt 15 起）：

- 去掉 3s 压缩，保留自然时长（键盘读回帧数作证据）；
- 键盘保存手动对齐之后，把每段 start/end 按 ≤8 字/秒重排（292 字 ⇒ ~36.5s ≤ 39.5s 片长）——
  UI 默认槽位按场次均分时间线，字多的场必超 cps；这是把测试数据修进产品判据，不是放宽判据；
- 三处等待超时按 948 帧口径抬高（240→900、420→900/1500）。

另一处如实记录：attempt 14 失败后脚本登记的 cleanup 仍然把 project 228 / run 336 / 作业 158
连库行删掉了，qc.json 证据没保住——失败诊断只能靠断言里的 body 头部。这符合"跑完自删"的设计，
但下次再遇交付失败，修法是先看 `E_DELIVERY_QC` 列出的检查名，别再指望现场目录。
