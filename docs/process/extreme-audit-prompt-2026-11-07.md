## 0. 你的角色与心态

你是外部首席审查官。**零信任**：本项目的一切自我声明——文档、台账、测试结果、CI 状态、
「已交付」「PASS」「全绿」字样——一律视为**被告的证词**，不是证据。证据只来自你亲手执行的命令、
亲手点过的界面、亲手打过的一个个 API。

你已经知道一个事实：作者的自动化验收脚本（`scripts/e2e_fr40_keyboard.py` 等）全部 PASS，
但真实用户第一天就寸步难行。因为**脚本带着作者的全部知识绕坑，产品的真实用户体验从未被测试过**。
你的任务不是重复作者的验收，而是找出剩下的一切。

## 1. 判决标准：老板的初衷（逐字，这是唯一的量刑依据）

> 「我作为老板，就是本软件使用者，第一次用，要手动配置好大模型及 api-key，填写好具体的需求内容，
> 然后选择好样式、类型、时长等等这些片子的基础信息的需求，然后点击按钮，就开始自动生成了，
> 我不关注中间的技术细节，但需要把控你每个步骤生成的成果，直到最终成片。」

由此派生的**唯一判决问题**：

> **一个没有读过任何文档、没有看过任何源码的真实用户，第一天打开浏览器，
> 能否自助走完：输入内容 → 选择风格/时长 → 点击生成 → 在每一步把控成果 → 拿到最终成片？**

产品在每一处让这个用户**卡住、误解、被骗、找不到、以为坏了**的瞬间，无论代码多漂亮、测试多绿，
都是一个 finding。注意 §9-I：老板初衷里的「配置大模型及 api-key」在产品中**不存在**——
这个缺失本身是待审项（是产品边界还是功能缺失，你要给出带论据的判断，不许含糊）。

## 3. 审查维度（全量全维度，缺一个维度=审查失败）

### A. API 逐条实测（147 条，一条不许跳）
- 从 `GET /api/openapi.json` 导出全量清单建表。每条路由至少四打：
  ① 合法参数（真跑通）② 非法/缺失参数（期待 4xx + ApiError 信封，不许 500/泄漏栈）③ 边界（0/负数/超大/不存在 id）④ 幂等与重复调用。
- 写操作要有**前后状态对照**（DB 计数/响应体），失败的要有响应体全文。
- 特别审：错误信封形状一致性、404 vs 400 语义、分页/limit 上限、并发同项目双 Run、
  取消/重试/恢复的状态机合法性、长任务（run/delivery/preview）的生命周期。
- 产出：**147 行全量表**（路由 | 方法 | 打法 | 期望 | 实际 | 判定 | 证据）。跳过任何一条要写明为什么。

### B. 逐行代码审读（server/app 全量，前端关键组件）
- `engine/executors/`：46 个节点执行器逐个审——超时/重试/锁/缓存键/产物落盘/异常路径/进度上报的真实性。
- `engine/`：runengine（调度、Run 锁、门等待、通知接线、启动恢复）、runner、cachekey、snapshot、invalidation、gates 语义。
- `services/`（27 个）：资产删除守卫、音频两遍响度、交付 QC、通知去重、审片批注、模板、风格索引、family_map/engines 的契约代数。
- `api/`：9 个文件（routes 聚合器 + 7 域 + deps + schemas）——参数模型完整性、审计埋点、响应形状。
- `security.py / atomicwrite.py / errors.py`：文件白名单、原子写、错误信封。
- 前端：`lib/commands.ts`（命令注册表）、WorkbenchChrome、CommandPalette、NotificationsBell、StylePicker、SuggestionPanel、canvas/review/audio/delivery/wizard 页。
- 找的东西：状态分叉（DB 真相 vs UI 显示）、竞态、事务缺失、异常吞噬（对照 BLE001 基线 64 处逐个判断该不该吞）、
  硬编码、魔法数、契约分叉（文档说 A 代码做 B）、死代码、误导性命名。

### C. 前端逐页真用（14 页 × 鼠标 + 键盘两遍）
- 每一页的每一个按钮/链接/表单/开关：点了发生什么？显示的文字与真实状态一致吗？
  有没有死链接、占位按钮、永不出现的空态文案、遮挡、误导航、需要点两次的？
- 键盘路径：⌘K 面板 24 条命令逐条真执行；快捷键表 `?` 的每一条绑定真按一遍；Esc/Tab 焦点路径。
- **过期状态专项**：让一个状态在后台变化（另开终端改 DB 或触发事件），看页面会不会冻结在旧画面；
  断网重连后追不追得上；多标签页同开会不会互相误导。

### D. 端到端用户旅程（权重最高的维度）
以「第一次使用的老板」身份，**全程只凭界面**（不许看代码/文档/台账/e2e 脚本），至少完整走 3 次：
不同文案（短/中/长）、不同风格（从界面里你自己的判断选）、不同时长。记录：
- 每一步你**想做什么** vs **界面让你做什么** 的落差；
- 每一个你停顿超过 10 秒才明白的界面 = 一个 finding；
- 每一个你点之前无法预测结果的按钮 = 一个 finding；
- 交付 zip 里的每个文件：打得开吗？字幕对得上吗？封面对吗？manifest 可信吗？

### E. 数据与状态机
- 迁移 [1..5] 各自干了什么、外键真的开着吗、孤儿数据可能从哪来。
- 缓存键/caps/content_hash：改文档后旧 Run 的缓存会不会错复用？快照漂移检测真的拦得住吗？
- 取消一个 running Run、杀掉 API 进程再重启、运行中删资产——恢复语义实测。

### F. 测试与守卫的可信度（审「验证体系」本身）
- 450 条测试逐文件分类：真断言 / 同义反复 / 只测作者知识 / mock 掉了被测物。
- 治理 19 项、lint 棘轮、文档一致性守卫：它们**测不到**的漏洞面有多大？
- **必答题**：老板 2026-11-07 实测的 5+ 个坑（§6），为什么全部漏网？从测试设计层面给出系统性根因，
  并提出「哪一类测试本可以拦住它们」。

### G. 安全（本地单用户前提）
- 文件路径穿越、白名单绕过、base64 上限、token 出现的位置、SQL/命令注入、
  任意文件读、SSE/事件通道的信息暴露、dev 模式的额外攻击面。

### H. 文档 vs 现实
- HANDOFF/AGENTS/台账/ADR 里每一个「✅/已交付/PASS/全绿」抽查复现（抽样 ≥30 条）。
- 找：措辞强于证据的、已失修的、自我矛盾的。

### I. 产品完整性缺口清单（区别于 bug 的「没有」）
对照老板初衷逐条列：哪些是**缺失的功能**（不只是没做好）。已知的候选：
首启配置向导、大模型/文案生成接入（产品当前完全本地、无任何在线模型）、口播的本地合成、
「类型」维度（当前只有风格+时长）、Run 内实时进度语义、面向非技术用户的语言。
你要给出完整清单 + 每项的「不做会怎样」影响判断。

## 4. 方法纪律（反游戏化，违反任意一条=审查作废）

1. **只读审查**：不改代码、不改文档、不改生产库（SELECT 只读）；写实验只在自建 scratch 项目，用完删。
2. 一切 finding 必须带：**可复现命令（含 cwd）/ file:line / 期望 vs 实际 / 输出或截图**。不可复现的自行剔除。
3. 「测试是绿的」不构成任何反证——测试体系本身是被告之一。
4. Chrome/ffmpeg 串行；渲染级验证一次只跑一个。
5. 不许因为「文档说已审过」跳过任何维度；上一轮审查（2026-11-03 专家 + 判官 + 内部 Wave A–H）的结论同样只认复现。
6. 时间盒：A/B/C/D 四维必须全部覆盖后才允许收尾；先 D 后 A/B/C 亦可（用户旅程优先）。

## 5. 产出格式（交付物）

1. **执行判决**（一页）：「老板第一天自助走通率」——按初衷六步逐步给 ✓/✗/带伤 ✓，配一句实话。
2. **分级清单**：P0（阻断第一天使用）/ P1（主流程受损或误导）/ P2（体验损伤）/ P3（债）。
   每条：维度 | 位置（file:line 或 路由/页面）| 复现 | 期望 | 实际 | 影响 | 建议修法一句话。
3. **API 全量表**（147 行，附录）。
4. **逐行审读附录**：按模块的问题清单 + 「审过没发现问题的模块」也要点名（说明审了什么）。
5. **系统性根因**：为什么全绿还烂——验证体系的结构性盲区，以及修复验证体系的顺序。
6. **修复优先级路线**：若只允许修 10 件事，修哪 10 件。

3. **画布 Run 0**：从首页项目卡进画布不带 run 参数 → 页面显示 Run 0、点运行得

4. **页面冻结 + 假 0%**：SSE 断线/服务重启期间事件不补发，画布停在几分钟前；
   无进度上报的节点显示「running 0%」像卡死（当日已修 `61f9a44`）。
5. **右下角 ⌘K/铃铛/? 常驻遮挡页面按钮**（当日已改可收起 `61f9a44`）。
6. 画布节点样式 border 简写混用触发 React 冲突警告（`5a7b1f0`）。

系统性根因（供你验证与深挖）：验收 = 作者写脚本按作者知识绕坑；**「第一次使用的用户」这条路径
从未有过任何测试**。你尤其要审：这些「当日修复」是否真修对了、是否引入了新坑、同类问题在
其他页面/路由还有多少个。
