# FilmFlow 开发全生命周期流程（SDLC）

> 版本 v1.0 · 本文档定义"代码怎么被生产出来"。产品需求看 PRD，技术细节看规格，行为契约看 `bdd/features/`。

## 1. 角色与职责

| 角色 | 担任 | 职责 |
|---|---|---|
| 老板 / 产品经理 | 用户 | 验收演示、优先级裁决、规格变更**唯一批准人**、补标队列责任人 |
| 开发模型 | ZCode | 技术方案、BDD 场景增补、TDD 实现、演示交付、文档同步 |
| 质量内建 | 自动化 | pytest-bdd 场景 + pytest 单测 + Playwright E2E（无人工 QA 层，老板验收即最终门） |

## 2. 生命周期总览

```
S0 工程准备（规格三轮审查 ✅ / PRD ✅ / 本 SDLC 包 ✅）
S1 技术方案  —— §18 九项方案（tech-plan.md），老板确认后才准写生产代码
S2 BDD 场景  —— 每个 Feature 先有 .feature 文件（本包已建 15 个；story 实现前允许增补，增补需在 commit 中说明）
S3 TDD 实现  —— 红 → 绿 → 重构，循环提交（见 §4）
S4 里程碑验收 —— 每期结束跑 demo，对照规格 §13 验收句逐条打勾
S5 回顾与回写 —— 新裁决写回规格 §19；新知识写 ADR
```

**硬规则：S1 方案未确认，不写一行生产代码；.feature 场景未定，不写该 story 的实现。**

## 3. Milestone 内部循环（每个 Story 的生命周期）

```
拉取 Story（features.md 表）
  → 确认/增补 gherkin 场景（老板可见的行为契约）
  → DoR 检查（见 §5）
  → TDD 循环：失败单测(红) → 最小实现(绿) → 重构 → 全绿
  → 集成：跑通所属 .feature 场景（pytest-bdd）
  → E2E：Milestone 收尾统一跑 Playwright
  → 演示：给老板跑验收场景
```

## 4. TDD 工作规约

1. **先测试后实现**：每个执行器/解析器/状态机，先写失败的单元测试再写实现；红绿各自 commit。
2. 单测三件套优先级：**命令构造与输出解析 > 状态机转换 > 失效图传播**。执行器的验收线是"给定 fixture 输入 → 断言产物哈希/指标"，不是 mock。
3. 禁止 mock 生产路径（规格 §15.10）：Chrome/ffmpeg 调用在集成与 E2E 层用真实二进制；单元层只允许 mock 子进程边界（spawn 调用本身），进度协议 `@@PROGRESS` 必须按真实 NDJSON 解析。
4. 重构纪律：全绿之后才允许重构；重构 commit 不改行为（gherkin 场景不得因重构而改）。

## 5. Definition of Ready / Done

**DoR（一个 story 可以开工的条件）**
- [ ] 对应 .feature 文件存在且场景覆盖验收标准
- [ ] 依赖的裁决在规格 §19 有出处（不得与裁决冲突）
- [ ] 需要的夹具在 test-strategy §5 映射表中有归属
- [ ] 依赖的 API/数据对象在 tech-plan 中已定义

**DoD（一个 story 可以验收的条件）**
- [ ] 新增/修改代码 100% 先有失败测试后实现（commit 历史可查）
- [ ] 所属 .feature 全场景绿（pytest-bdd）
- [ ] 覆盖率达到 test-strategy §4 目标（变更行覆盖，不是全仓平均）
- [ ] 无 TODO / 无 any(typed placeholder) / 错误码进枚举
- [ ] 涉及行为变化的文档（规格/PRD/ADR）已同步
- [ ] 可演示：老板能在 running 的 app 里亲手走到该行为

## 6. 分支与提交

- `main`：里程碑验收后才快进；验收之间开发在 `feat/<F-ID>-<slug>` 分支。
- Conventional Commits：`test:`（红）→ `feat:`（绿）→ `refactor:`（重构）→ `docs:`。commit message 必须带 F-ID（如 `feat(F04): 引擎注册表与可用性门`）。
- 每个 red-green-refactor 循环至少一次 commit；禁止"一把梭"大提交。

## 7. 变更管理（宪法条款）

1. 规格 **§19 裁决表是宪法**：任何实现不得与裁决冲突。
2. 实现中发现的规格缺陷 → 开发提 issue 式说明（影响面 + 建议）→ **老板批准** → 修改规格 + §19 加行 + 必要时 ADR → 代码才可偏离。
3. 所有技术选型变更必须记 ADR（`docs/adr/NNN-*.md`），含背景/备选/后果。
4. 三份文档的同步责任：改行为 → 同步 .feature；改数据结构 → 同步 tech-plan；改产品决策 → 同步 PRD + 规格 §19。

## 8. 里程碑验收仪式

每期结束：`./dev` 起服务 → 老板按规格 §13 对应验收句亲手操作 → 逐条打勾 → 不通过项回 S3。验收通过才允许进入下一期，`main` 打 tag（`m0`、`m1`…）。
